# ADR-001: Modular Monolith Architecture

**Date:** 2026-10-23  
**Status:** Accepted  
**Deciders:** Technical lead (following development plan)

## Context

ALMATRACE is a departmental web application for approximately 50–200 users
at launch (pilot). The team is small (3–5 people). The institution may not
have DevOps capacity for complex infrastructure.

## Decision

Use a **modular monolith**: a single deployable Node.js/Express service with
clearly defined internal module boundaries.

Modules: `auth`, `people`, `departments`, `matching`, `mentorship`,
`notifications`, `moderation`, `admin`, `platform`.

Each module owns its routes, business logic, and database queries. Modules
communicate via explicit function calls (not HTTP or message queues) and
through shared database transactions where needed.

## Rationale

- Correct for the expected scale and team size.
- Development plan explicitly recommends it: "Use a modular monolith for
  the first release; do not start with microservices."
- Simple deployment: single process, single database.
- Module boundaries make future extraction possible if operational needs
  change — but extraction should only happen when justified by evidence.
- Easier to reason about cross-cutting concerns (auth, audit, sessions).

## Consequences

- All modules share the same database schema (by design at this scale).
- A bug in one module can affect others — requires careful error handling.
- Deployment is all-or-nothing per release (acceptable at this scale).
- Must enforce module isolation in code review, not in infrastructure.

# ADR-002: PostgreSQL as sole data store

**Date:** 2026-10-23  
**Status:** Accepted

## Decision

Use PostgreSQL for all persistent storage: user data, sessions, jobs,
notifications, imports, and audit events.

No Redis, no Elasticsearch, no separate search service for MVP.

## Rationale

- Avoids operational complexity of multiple data stores.
- PostgreSQL full-text search is sufficient for profile/interest search at
  this scale.
- `connect-pg-simple` stores sessions in PostgreSQL, eliminating Redis.
- Background jobs are tracked in a `notification_deliveries` table, not a
  separate queue.
- The team can reason about one data store and one backup target.

## Consequences

- Session and job storage adds tables to the database.
- PostgreSQL must be available for the application to function (no in-memory
  fallback).
- Full-text search is limited; if this becomes insufficient, an index service
  can be added later.

# ADR-003: Token rule as pluggable interface (UNCONFIRMED D1)

**Date:** 2026-10-23  
**Status:** Active (pending D1 resolution)

## Context

The department's token matching rule is UNCONFIRMED. The development plan
identifies this as a hard stop: "Do not implement or import real records
using an assumed roll-number/token formula."

## Decision

Implement the token rule as a **pluggable interface**:

1. `token_rules` database table stores rule type and JSONB configuration.
2. The matching engine reads the active rule and delegates to a rule handler.
3. Rule handler interface: `{ normalize(rawId): string, matches(keyA, keyB): boolean }`.
4. Only a `synthetic` handler is implemented until D1 is resolved.
5. `TOKEN_RULE_MODE=synthetic` in env prevents real matching from running.

## Consequences

- No production token matching until D1 is approved.
- Adding a new rule type requires implementing a handler and creating a
  migration to add the rule configuration.
- All matching is versioned: the rule ID and version are stored on every
  token_link record.
